REST
- REST, Representational State Transfer
- 웹 상의 자원(문서, 이미지, 동영상, 데이터 등)의 위치를 URL로 표현했었는데

URL로 표현하는 방법을 규칙으로 만들었다

자원의 상태를 주고 받기 위한 행동과 표현을 규칙으로 만들었다

웹 상의 자원을 URL 자체만 보고도 이게 뭔지 뭐하는건지 식별 가능하게 만들자는 취지

표준안은 없다

URI(URL)을 만들 때 규칙
- 회원 관리 > 각 기능의 URL 정의

1. 기존 방식
- URL > 주로 동사 + 명사를 사용
    - 동사: 업무(행동) 표현
    - 명서: 데이터 표현

[메서드]      [URI]
- GET         http://localhost:8080/member/list.do                목록보기
- POST        http://localhost:8080/member/add.do                 추가하기
- POST        http://localhost:8080/member/edit.do                수정하기
- POST        http://localhost:8080/member/del.do                 삭제하기
- GET         http://localhost:8080/member/list.do?word=검색어    검색하기


2. REST 방식

명사(여기선 member)로 데이터를 표현하고 메서드로 행위를 표현했다
REST 방식의 한계: 메서드가 얼마 없다(더 복잡한 업무일수록 표현하기가 힘들다)

[메서드]      [URI]
- GET         http://localhost:8080/member         목록보기(10명)
- POST        http://localhost:8080/member         추가하기(1명)
- PUT         http://localhost:8080/member/1       수정하기(1명)
- DELETE      http://localhost:8080/member/1       삭제하기(1명)
- GET         http://localhost:8080/member/검색어  검색하기

REST API 설계 규칙
1. URI에서 자원(명사)을 표시한다.(주로 URI의 마지막에 표현)
2. URI에 동사를 표시하는 않는다.(무슨 행동을 하는지는 URI에 표현 안함)
3. HTTP Method를 사용해서 행동을 표시한다.
    a. GET:     서버로부터 리소스 요청
    b. POST:    데이터를 서버에게 전달 + 서버측 생성
    c. PUT:     데이터를 서버에게 전달 + 서버측 수정(전체 수정)
    d. PATCH:   데이터를 서버에게 전달 + 서버측 수정(일부 수정)
    e. DELETE:  데이터를 서버에게 전달 + 서버측 삭제
    
4. URI + HTTP Method = 완성

5. 구분자는 '/'를 사용한다.
6. URI의 마지막에 '/'를 적지 않는다.

7. '-' > 권장(가독성)
8. '_' > 비권장(가독성)
9. 확장자를 사용하지 않는다.

10. REST API의 요청 결과(반환값)는 순수 데이터만 반환한다.
    - JSON, XML, Text
    - HTML을 반환하지 않음
    - ajax용 서버로 사용
    - REST 구현 > 클라이언트(브라우저, 모든 기기)
